# Local supervised execution

The harness has a persistent local worker and a systemd transport for one trusted Linux host, with durable terminal cleanup evidence and a required execution-time deadline gate. The worker records start intent before contacting the manager and never uses an existing intent to start again. **CoworkeRL training is not enabled.** Source/input byte verification is implemented separately; immutable deployment, environment/native qualification and an actual CoworkeRL execution backend remain prerequisites.

This description covers source `521ceba91b770b87a3c8a9094425fbcc60b1c3ac`. [CI run 41396062992](https://github.com/ronoktanvir/rl-research-harness/actions/runs/41396062992/job/125117528860) passed seven native Linux cases and their parent test: eight passes in 14.465 seconds. The required `Type=notify` path retained lifecycle/cleanup behavior, refused delayed execution and denied actual main-PID runtime-extension attempts. These new results qualify the tested protocol on that CI image; earlier `Type=exec` results alone did not.

## Ownership and interfaces

`src/execution/types.ts` defines the commands, deployment profile, host/unit identity, observations and journal contract. `journal.ts` owns a separate SQLite database with one controller owner, immutable job/action identities and append-only receipts. `systemd.ts` implements bounded native manager calls; `deadline-gate.ts` and its trusted Python helper build and enforce the pre-execution time check. `worker.ts` coordinates those components, including uncertainty, current authorization and serialized operations for each job.

Trusted deployment code constructs a declaration with `createJobDeclaration`, then calls `createSupervisedWorker({journal, transport, workerId, authorize})`. Its operations are `launch(declaration, signal)`, `query(jobId, signal)` and `cancel(jobId, signal, authorizeCancellation)`. Cancellation requires its own fresh authority callback after the manager ownership query. Results retain the exact observation ID/sequence; cancellation additionally exposes its own stop-command status and receipt, distinct from launch acceptance. The [ledger-connected backend](supervised-backend.md) supplies this wiring for admitted local operations. There is no general model-facing shell endpoint or training-launch CLI.

The declaration binds the action/backend key, manifest, plan, host/boot identity, literal command, limits and deadline. Unit identity derives from the worker and backend key; the description binds the full declaration. Launch reconstructs that identity and refuses changed or forged declarations. The host, command and limits are declarations until the deployment layer verifies their real provenance.

The required `authorize` callback is trusted synchronous application code. It must check the actual current authority, not a cached model decision. Authorization is checked before creating intent and again immediately before the native manager invocation, after asynchronous transport preflight. Cancellation can address an owned existing job while new launches are stopped. Query never starts, resets or deletes a unit.

## Durable start and recovery

The journal uses WAL with `synchronous=FULL` and a crash-released lifetime ownership lock in a service-owned local directory. It rejects foreign/unsupported stores and conflicting job/action declarations. Existing records return `created:false`; this is evidence of an earlier intent, never replay authority. A genuine process-kill test verifies the difference between an uncommitted transaction and committed intent.

After a lost launch response, matching supervisor evidence can establish acceptance. An empty listing, host reboot, malformed response or unreachable manager cannot establish nonacceptance after intent. Repeating launch queries the original identity. It does not generate a new unit or replace the journal. A crash between recording intent and sending the request can therefore leave an unstarted job uncertain; automatic retries would risk duplicate work.

Acceptance, process state, cancellation requests and cleanup evidence are distinct. Accepted receipts must bind the declared unit and host. Once an invocation has been observed, subsequent queries and cancellation pin that invocation. Malformed or conflicting observations are retained as unknown outcomes. Previously confirmed terminal process outcomes survive later cleanup and unit removal; a stop request cannot rewrite success as cancellation. No process outcome establishes scientific validity or paid allocation release.

## Native transport

The transport requires Linux, a running systemd manager at version 254 or later and cgroup v2. A trusted profile fixes non-root UID/GID, executable and environment allowlists, read-only roots, writable root, maximum resources and the required `deadlineGate` configuration. That configuration declares the trusted interpreter/helper paths, safety margin and notification-barrier timeout. The helper must be in a declared read-only root, and the interpreter, libraries and helper must be immutable to the trainer. Use a separate profile/writable root per job when jobs must not modify each other's outputs. Keep the journal and controller data outside the writable root. These are deployment obligations, not facts inferred from path strings or a matching file hash.

Manager access uses fixed binaries and, when explicitly configured, a fixed noninteractive sudo prefix. The trainer remains non-root. Commands use literal arguments, an empty inherited environment and explicit nonsecret values. Job declarations are stored in the journal, so credentials must not be inserted into them. The current transport has no training-credential provisioning integration.

Systemd controls active runtime, startup/stop intervals, memory, tasks and the owned cgroup, with no restart or cgroup delegation. The fixed protocol uses `Type=notify`, initial `NotifyAccess=main`, no runtime randomization and no `ExecStartPost`. Filesystem and privilege protections narrow the service's access. This configuration and its tests do not establish hostile-code isolation or verify every host policy.

The transport masks `/run/systemd/private`, `/run/dbus`, `/run/docker.sock` and `/run/containerd`, when present. It must leave `/run/systemd` itself accessible: systemd 255 creates an incoming mount under that directory and remounts it during namespace setup. The broader original mask was incompatible with that path; the subsequent Linux run reported `226/NAMESPACE` before the fixture executed. The narrowed mask preserves the manager's namespace machinery while restricting its private control socket. Real [Linux qualification](systemd-qualification.md) now passes startup and separately verifies denied read/write permissions on that endpoint from each observed fixture process. This is a specific pathname observation, not universal IPC isolation. [Observed namespace failure](https://github.com/ronoktanvir/rl-research-harness/actions/runs/41393036492/job/125108345465), [incoming directory setup](https://github.com/systemd/systemd/blob/v255/src/core/exec-invoke.c#L3085-L3092), [required remount](https://github.com/systemd/systemd/blob/v255/src/core/namespace.c#L2592-L2595), [private manager endpoint](https://github.com/systemd/systemd/blob/v255/src/core/dbus.c#L937-L944).

The manager job queue itself still has no configured timeout. The diagnostic Linux run rejected the transient `JobTimeoutUSec` property generated from `JobTimeoutSec`; systemd 255's setter processes that field but falls through without returning success. The transport omits that property while retaining activation, runtime and shutdown limits. The new gate addresses late trainer execution after queuing: it refuses execution if the remaining deadline cannot accommodate the configured runtime, shutdown grace and margin. It does not remove a pending manager job or establish a queue-latency bound. Literal argument handling remains enabled. [Observed CI diagnostic](https://github.com/ronoktanvir/rl-research-harness/actions/runs/41392837686/job/125107754374), [systemd 255 setter](https://github.com/systemd/systemd/blob/v255/src/core/dbus-unit.c#L2034-L2045).

The trusted helper starts with an empty inherited environment, sends readiness together with notification-access revocation, then waits for the manager's separate notification barrier before checking time again and replacing itself with the trainer. Trainer environment is supplied only to the final execution, so per-attempt loader settings cannot alter the helper. Disabling later notifications prevents the same-PID trainer from extending its runtime timer. Manager acceptance means the gate reached readiness; its final check or trainer execution may still fail. Acceptance does not establish trainer readiness or native preflight success. The notification endpoint `/run/systemd/notify` must remain reachable. See [the deadline protocol](execution-deadline.md).

Terminal cleanup no longer depends on the manager retaining a cgroup path. The transport brackets an exact owned cgroup v2 empty/absent observation with matching loaded terminal unit/invocation snapshots, preserves the manager's actual path field and appends identity-bound `cleanupEvidence`. The journal validates that proof before the worker uses it. [CI run 41395292611](https://github.com/ronoktanvir/rl-research-harness/actions/runs/41395292611/job/125115199740), at `0ded185b603fa09064b4ed22885d8c03f2a45c62`, observed native cgroup absence and false occupancy despite an empty manager path; worker cancellation became `accepted/failed`, preserving the manager's timeout result across reopening. Unestablished kernel evidence remains unknown, and a missing MainPID or absent unit alone never supplies cleanup proof. See [cleanup semantics and limits](cleanup-evidence.md).

## Qualification boundary

Offline tests exercise journal crash windows, exact identities, lost replies, concurrency, late callbacks, fresh authorization, malformed evidence and terminal-state preservation. The separate [Linux qualification suite](systemd-qualification.md) runs short CPU fixtures only when explicitly enabled and records actual manager/process evidence.

The deadline gate is implemented, required and qualified by the bounded native tests above. It combines wall UTC with the dispatch UTC advanced by elapsed boot time, so a later wall-clock rollback cannot increase allowance; boot mismatch fails closed. Completion within the declared UTC deadline remains conditional on initial clock accuracy, a shared host/boot time basis, bounded timer/scheduling/exec/kill delay and no suspend after activation. The safety margin is an operator-supplied bound, not measured assurance; the native minimum is 1,000 ms. Reboot, manager failure, administrator interference and unkillable kernel operations remain outside that claim. Acceptance receipts therefore retain `deadlineQualification: "conditional_local_host"` and `absoluteDeadlineEnforced: false`.

The [artifact verifier](integrations/coworker-artifact-verification.md) proves only observed source/input byte equality; it leaves deployment immutability, interpreter/image/dependency identity and native checks pending. Remote authentication/fencing, full CoworkeRL/GPU qualification, provider resource release and off-host recovery also remain unfinished. Neither a gate acceptance nor cleanup proof settles costs or authorizes a training campaign.
